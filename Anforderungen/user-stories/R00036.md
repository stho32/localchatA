# User Stories — R00036 Tabs auf dem Beitreten-Bildschirm folgen dem Beitritt eines Nachbar-Tabs

Für jedes Szenario gilt, wenn nicht anders genannt: die Instanz läuft auf einem freien Port, `localchatA` enthält den Channel `allgemein`, alle Tabs gehören zu **einem** Browser(-Kontext) auf `127.0.0.1`. Jedes Szenario einmal mit SharedWorker und einmal ohne (`delete window.SharedWorker` im Init-Skript), je mit 2 und mit 3 Tabs. „Binnen 1 s“ zählt ab der Antwort auf den Beitritt in Tab A.

## F0127 Tabs auf dem Beitreten-Bildschirm folgen dem Beitritt eines Nachbar-Tabs

### US-1: Ich trete in einem Tab bei, die anderen folgen

Rolle: **Teilnehmer mit mehreren Tabs** (Mensch im Browser), der zum ersten Mal die Seite öffnet.

Als Teilnehmer mit mehreren Tabs möchte ich nur in einem Tab beitreten, damit ich in den anderen nicht noch einmal tippen oder neu laden muss und nicht versehentlich ein zweiter Teilnehmer werde.

- **Gegeben** Tabs A, B (und C) stehen auf dem Beitreten-Bildschirm, es gibt weder ein gemerktes Token noch einen gemerkten Namen; in B ist `abc` im Namensfeld getippt
- **Wenn** ich in A als `shoff` beitrete
- **Dann** zeigen alle Tabs binnen 1 s die Kopfzeile mit `shoff@127.0.0.1` und die Teilnehmerliste mit `shoff` genau einmal, B zeigt kein Namensfeld mehr, und der Browser hat genau einen `POST /api/beitreten` gesendet
- **Und** ein Beitritt als `shoff` über die API von einer anderen Herkunft (`127.0.0.2`) ergibt 409: der Name ist einmal belegt
- **Und** die Konsole zeigt keine unbehandelte Ausnahme und keinen Verstoß gegen die Inhaltsrichtlinie

### US-2: Name vergeben — der Nachbar tritt neu bei, meine wartende Nachricht geht nicht verloren

Rolle: **Teilnehmer mit mehreren Tabs** nach einem Neustart der Instanz (wie R00025 US-11).

- **Gegeben** A und B sind als `shoff` in der Hauptansicht; die Instanz wurde neu gestartet; von derselben Herkunft ist per API `shoff` beigetreten, der Name ist vergeben; in B steht im Feld der Entwurf `noch offen`; B hat `fünf` gesendet, der stille Wiederbeitritt scheiterte mit 409, beide Tabs zeigen „Name vergeben“, B zeigt „1 ungesendete Nachricht wartet auf den Beitritt — Neuladen verwirft sie.“
- **Wenn** ich in A als `shoff2` beitrete
- **Dann** zeigt B binnen 1 s die Kopfzeile mit `shoff2@127.0.0.1`; `fünf` steht in `# allgemein` fehlgeschlagen mit „Nicht gesendet — der Beitritt war abgelaufen.“, „Erneut senden“ und „Verwerfen“; seit meinem Klick in A wurde genau ein `POST /api/beitreten` und kein `POST …/nachrichten` gesendet; im Feld von B steht weiter `noch offen`
- **Wenn** ich in B auf „Erneut senden“ klicke
- **Dann** steht `fünf` genau einmal im Verlauf, gesendet von `shoff2`

### US-3: Zwei Klicks im selben Augenblick ergeben einen Teilnehmer

Rolle: **Teilnehmer mit mehreren Tabs**, der in zwei Tabs fast gleichzeitig „Beitreten“ drückt (Browser mit Web Locks).

- **Gegeben** A und B stehen auf dem Beitreten-Bildschirm; in A steht `shoff`, in B `bert`
- **Wenn** ich in beiden Tabs im selben Augenblick „Beitreten“ klicke
- **Dann** zeigen beide Tabs dieselbe Kennung (die des Tabs, dessen Beitritt zuerst gelang), der Browser hat genau einen `POST /api/beitreten` gesendet, und am Server gibt es genau eine Sitzung dazu

### US-4: Kein Fehlalarm — ein abgelehntes Token führt nirgendwohin

Rolle: **Teilnehmer mit mehreren Tabs** (Grenze und Fehlerfall).

- **Gegeben** der Tab steht auf dem Beitreten-Bildschirm, weil sein Token abgelehnt wurde; in einem Nachbar-Tab geht ein Token verloren oder dasselbe abgelehnte Token wird erneut geschrieben
- **Wenn** das Ereignis im Tab ankommt
- **Dann** bleibt der Bildschirm mit seinem Zustand und seiner Eingabe stehen, es gibt keine Anfrage und keinen `POST /api/beitreten`; ist das gemeldete Token ungültig (401), bleibt der Bildschirm ebenfalls stehen, das Formular ist wieder frei, und das Token im Speicher bleibt unberührt (ein dritter Tab, der danach lädt, tritt nicht neu bei)

Nicht als Szenario, sondern als Kriterium (kein Mensch beobachtet es von außen): reine Funktionen `nachbarFolgen` und `vomBildschirmBeitreten` mit gestelltem Speicher und gestellter API sowie die drei Mutanten (Lauscher nicht angemeldet, Folgen per `beitreten`, Löschen bei 401) aus den Akzeptanzkriterien. Der Entwicklertest prüft US-1 und US-2 von Hand; US-3 ist von Hand kaum in einem Task auslösbar und läuft über die Abnahme-Probe, sonst „nicht beobachtbar — dein Urteil“. Ein Beitritt ohne Web Locks (unsicherer Kontext) kann bei gleichzeitigen Klicks zwei Sitzungen ergeben — in Kauf genommen (ADR-0012).
